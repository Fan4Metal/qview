# Производительность qview

[English version](PERFORMANCE.md) · [README](../README.ru.md)

В этом документе собраны замеры, на которых основано устройство qview: на что уходит время от запуска до просмотра изображения, оценки, сделанные перед изменениями, и принятые по ним решения. Все цифры получены на тестовой машине, описанной ниже, если не указано иное; цифры для другого оборудования являются оценками и помечены как таковые.

## Тестовая машина

| | |
|---|---|
| Процессор | Intel Core i7-13700KF |
| Видеокарта | NVIDIA GeForce RTX 4070 Ti SUPER (драйвер 32.0.16.1074, NVIDIA 610) |
| Монитор | 3840×2160, 240 Гц, масштаб Windows 150% |
| Память | 32 ГБ |
| ОС | Windows 10 Pro 22H2 |

При 240 Гц кадр длится 4,2 мс, при 60 Гц — 16,7 мс. Времена работы видеокарты ниже сравниваются с обоими бюджетами.

Часть поздних замеров сделана на второй машине: Intel Core i7-12700K, NVIDIA GeForce RTX 4070 Ti, 32 ГБ; они помечены и с цифрами выше не сравниваются.

## Запуск

| Момент | Время от создания процесса |
|---|---|
| Вход в `main` | ~20 мс |
| Окно создано | ~145 мс |
| Первый кадр | ~160 мс |
| JPEG 14,7 Мп декодирован (параллельно) | ~80 мс декодирования (декодером библиотеки `image`; JPEG на диске теперь идёт через декодер Windows, см. [Декодирование](#декодирование)) |

- Загрузчик создаётся, а файл из командной строки запрашивается до `eframe::run_native`, поэтому декодирование идёт одновременно с созданием окна; ограничением служит создание окна, а не декодирование.
- Отрисовка выполняется через glow, а не wgpu; стандартные возможности eframe (accesskit, wgpu) отключены.
- Значок окна растеризуется в `build.rs` при сборке; растеризация при запуске занимала 6 мс.
- Окно при запуске скрыто (`DWMWA_CLOAK`) и показывается после трёх нарисованных кадров (окно, сохранённое развёрнутым, создаётся обычным, разворачивается скрытым и показывается уже развёрнутым); это устраняет белую вспышку, а не экономит время: Windows показывала окно раньше, чем его первый кадр попадал на экран. Окно появляется примерно на три периода обновления экрана позже, чем раньше (оценка: 12,5 мс при 240 Гц, 50 мс при 60 Гц; не измерено).
- Список декодеров WIC (`wic::extensions`) заранее читается потоком из `main`.
- Шейдер фильтрации (см. [Фильтрация](#фильтрация)) никогда не собирается до появления первого изображения на экране.
- Значки (программы и 16 типов файлов, по 8 размеров) хранились как 32-битные слои BMP: по 306 КБ, из них 264 КБ — слой 256 пикселей, всего 5,2 МБ из 18 МБ exe. Слой 256 пикселей теперь хранится в PNG (Windows читает слои PNG в значках начиная с Vista; проверено извлечением из exe через `PrivateExtractIconsW`): ~50 КБ на значок, всего 0,85 МБ, exe — 13,2 МБ. Меньшие слои остаются BMP, которые Windows рисует без декодирования.
- Библиотека времени выполнения C компонуется статически (`crt-static`, `.cargo/config.toml`), чтобы qview не требовал Visual C++ Redistributable; это добавляет к exe ~180 КБ. Для запуска это даже немного выгоднее: пустая программа запускалась и завершалась за 6,31 мс (медиана 300 запусков) против 6,70 мс с загрузкой `VCRUNTIME140.dll` и библиотек `api-ms-win-crt-*`, то есть на ~0,4 мс быстрее.
- Тексты лицензий, которые показывает «О программе» → **Лицензии…**, встроены как есть (`include_str!`): `licenses/THIRD_PARTY_NOTICES.txt` 198 КБ (158 крейтов и шрифты; 211 КБ до того, как из него убрали крейты процедурных макросов вроде `syn`, которые работают в компиляторе и в exe не попадают), LGPL 43 КБ, лицензия qview, `THIRD_PARTY_LICENSES.md` и лицензия UnRAR 5 КБ: ~245 КБ exe. Читаются они только при показе окна.

## Декодирование

### Пути

Каким декодером идёт файл (`loader::decode`):

| Файл | Декодер |
|---|---|
| JPEG на диске (определяется по первым байтам, не по расширению) | декодер Windows (WIC), см. [JPEG через декодер Windows](#jpeg-через-декодер-windows); библиотека `image`, если он не справился |
| HEIC/HEIF, AVIF | libheif в 8 потоков (dav1d для AV1), см. [HEIC и HEIF](#heic-и-heif) и [AVIF](#avif); WIC, если не удалось |
| RAW камер, JPEG XR, DDS и любой формат, для которого в Windows есть кодек | WIC |
| Всё остальное (PNG, GIF, WebP, TIFF, BMP, …) и любое изображение в архиве | библиотека `image`, формат угадывается по содержимому |

`loader::read`, которым пользуются повторное чтение для гистограммы, цвет под указателем, сохранение и миниатюры форматов, которые Windows не делает, для файла на диске сначала пробует библиотеку `image`, поэтому их цифры ниже — цифры `image`.

«Декодировано за N мс» в строке состояния — время рабочего потока на файл: чтение, декодирование, ориентация, BGRA с предумноженной альфой, mip-уровни и гистограмма при раскрытом разделе; загрузка текстуры не входит. Когда заняты два-три потока, оно больше времени одного потока, замеренного отдельно.

### Этапы

Замер для JPEG 14,7 Мп в потоке декодирования декодером библиотеки `image` (путь всех форматов, кроме JPEG на диске, и запасной путь JPEG):

| Этап | Время |
|---|---|
| Декодирование | ~80 мс |
| Перевод в BGRA с предумноженной альфой | ~14 мс |
| Все mip-уровни в линейном свете (sRGB декодируется по таблице, усредняется, кодируется снова; по умолчанию) | ~12 мс |
| Все mip-уровни по хранимым значениям (усреднение 2×2 по упакованным байтам; «Вид» → «Фильтрация» → «Уменьшать в линейном свете» выключено) | ~4 мс |

- Два или три рабочих потока берут файлы из очереди с приоритетами, которую интерфейс заменяет целиком, поэтому пропущенные пользователем файлы не декодируются.
- Всё, что нужно видеокарте (BGRA в родном для драйвера порядке и все mip-уровни), готовится в рабочем потоке; поток интерфейса ничего не преобразует.
- Уровень от миллиона пикселей (первые два у фото 14,7 Мп) строится полосами строк в четырёх потоках: в одном потоке уровни занимали 5 мс по хранимым значениям и 20 мс в линейном свете. `cargo test --release mip_timings -- --ignored --nocapture` измеряет оба способа на синтетическом изображении 14,7 Мп.
- `cargo test --release phase_timings -- --ignored --nocapture` с `QVIEW_BENCH_FILE` измеряет эти этапы для любого файла.

### JPEG через декодер Windows

JPEG на диске сначала декодирует Windows (WIC), zune-jpeg из `image` — только если это не удалось или в архиве. Декодер WIC не медленнее zune-jpeg и сам отдаёт BGRA с предумноженной альфой, так что перевод не нужен; на тяжёлых файлах он и быстрее. Замер на второй машине (i7-12700K) в потоке декодирования (чтение, декодирование, ориентация, BGRA; без mip-уровней):

| Файл | `image` + перевод | WIC |
|---|---|---|
| Фото 17,5 Мп, 4:2:0, 5,2 МБ | 66 + 21 мс | 63 мс |
| Постер 10,2 Мп, 4:4:4, 1,7 МБ | 30 + 12 мс | 32 мс |
| Серый скан 14,5 Мп, 6,3 МБ | 53 + 132 мс (до отдельного серого пути в `to_bgra`, теперь 13) | 55 мс |
| Скан 31,7 Мп, 4:4:4, 34 МБ (8,6 бит на пиксель, качество 12 в Photoshop) | 300–340 + 33–44 мс | 250 мс |

- Скан 31,7 Мп показывал в строке состояния «Декодировано за 422 мс»: к собственным 370 мс потока добавляются два других потока, декодирующих соседей, и попадание потока на E-ядро. При таком битрейте время уходит на декодирование Хаффмана, которое ни один декодер не делит между потоками; декодирование с масштабированием DCT (libjpeg-turbo) тоже мало помогло бы, энтропийное декодирование остаётся целиком.
- `phase_timings` печатает время WIC после этапов `image`.

Замерено и декодирование с масштабированием DCT (`wic_scaled`, вторая машина): декодер JPEG Windows реализует `IWICBitmapSourceTransform`, чей `CopyPixels` в половину, четверть или восьмую часть размера пропускает большую часть обратного DCT, апсемплинга и преобразования цвета и сразу отдаёт BGRA с предумноженной альфой.

| Файл | Полный размер | 1/2 | 1/4 | 1/8 |
|---|---|---|---|---|
| Фото 14,7 Мп, качество 90, 4:2:0, 3,0 МБ | 42 мс | 30 мс | 26 мс | 22 мс |
| Фото 17,5 Мп, 4:2:0, 5,2 МБ | 60 мс | 46 мс | 41 мс | 37 мс |
| Скан 31,7 Мп, 4:4:4, 34 МБ | 250 мс | 230 мс | 220–230 мс | 200–220 мс |

- Не используется: энтропийное декодирование, которое масштабирование не пропускает, занимает большую часть времени даже у обычного фото (восьмая часть пикселей всё равно стоит половину времени), а у тяжёлого скана — почти всё. Выигрыш 10–25 % в половинном размере, который был бы показан, оплачивался бы вторым, полным декодированием при зуме к 100 % и текстурой, которую нельзя дополнить из уже декодированных пикселей. Масштабированное декодирование libjpeg-turbo — та же сделка.

### HEIC и HEIF

| Способ | HEIC 12 Мп с iPhone |
|---|---|
| WIC, декодер освобождается после каждого файла | ~280 мс заголовок, ~500 мс декодирование |
| WIC, декодер сохраняется в потоке (`wic::keep_codec`) | ~5 мс заголовок, ~160 мс декодирование |
| libheif, 4 потока (по умолчанию) | ~120 мс декодирование |
| libheif, 8 потоков | ~95 мс декодирование |
| Заголовок через libheif без буферизации | ~25 мс (~30 000 мелких чтений) |
| Заголовок через libheif с `BufReader` на 64 КБ | ~1 мс |

- Освобождение последнего декодера HEIF в WIC останавливало его конвейер HEVC (~260 мс), поэтому каждый поток сохраняет по одному декодеру каждого использованного контейнера.
- Для HEIC/HEIF используется libheif с 8 потоками декодирования; WIC остаётся запасным вариантом.

### AVIF

AVIF передавался WIC, которому нужно расширение AV1 Video Extension из Microsoft Store; без него (как на тестовой машине) изображение не показывалось. Теперь в `heif.dll` встроен dav1d 1.5.4 (декодер AV1 от VideoLAN, с ассемблерным кодом NASM: AVX2 и AVX-512), и `heif::takes` передаёт AVIF в libheif, если DLL сообщает о наличии декодера AV1 (`heif_have_decoder_for_format`). Число потоков dav1d выбирает сам (по числу логических процессоров).

| Файл | libheif с dav1d | WIC без расширения AV1 |
|---|---|---|
| `example.avif` из libheif, 800x533 | ~1 мс заголовок, ~8,5 мс декодирование | ошибка (0xc00d5212) |
| 12 Мп (4032x3024, 8 бит, Pillow с качеством 75, 4,8 МБ) | ~0,2 мс заголовок, ~90–95 мс декодирование | ошибка |

AVIF на 12 Мп декодируется примерно так же быстро, как HEIC на 12 Мп с iPhone (~95 мс).

Миниатюры галереи: для AVIF и HEIC без расширений из Store у Windows их нет (`GetImage` отказывает за ~1 мс), поэтому файлы декодируются. Три фотографии AVIF 1920x1280 из интернета (8 бит, 4:2:0, без элемента миниатюры) заняли по 16–40 мс, большую часть — в dav1d (forest-path: 32 из 39 мс; остальное — перевод в RGBA в libheif): неподвижный кадр без тайлов декодируется в немногие потоки. Папка из 21 изображения (3 из них AVIF) через пул из 4 потоков миниатюр: все миниатюры за ~170–200 мс, AVIF — на 107–168 мс, вперемешку с остальными.

| Миниатюры | Время |
|---|---|
| Пример HEIC из libheif (1280x854), сторона 256, собственная миниатюра 320 пикселей (`heif::decode_within`) | ~4–5 мс |
| То же с декодированием целиком (сторона 768) | ~35–50 мс |
| 14 файлов AVIF/HEIC, 4 потока, dav1d на всех процессорах | 232–248 мс |
| То же, dav1d ограничен 4, 6 или 8 потоками (`num_codec_threads`) | 207–229 мс |

- Собственная миниатюра HEIF или AVIF (в HEIC с iPhone она есть, 320 пикселей) берётся, если она не меньше запрошенной стороны.
- Ограничение потоков dav1d для миниатюр дало ~8% и потребовало бы раскладывать `heif_decoding_options` вручную: не сделано.

| Размер | До | С dav1d |
|---|---|---|
| `heif.dll` | 1686 КБ | 3495 КБ (+1,8 МБ) |
| Установщик (LZMA) | 7,34 МБ (0.8.0) | 7,89 МБ (+0,53 МБ) |
| Портативный zip | 7,68 МБ (0.8.0) | 8,41 МБ (+0,71 МБ) |

dav1d встроен в `heif.dll`, а не поставляется отдельным `dav1d.dll` (лицензия BSD-2-Clause это допускает), поэтому набор файлов рядом с exe не изменился. Сборка только для 8 бит сэкономила бы примерно 0,8 МБ (оценка, такая сборка не проверялась), но фотографии AVIF часто 10-битные (HDR с телефонов), поэтому 10/12 бит оставлены. Функция `avif-native` крейта `image` (dav1d-sys, тот же декодер внутри exe) стоила бы примерно столько же и требовала бы pkg-config и заранее собранного dav1d.

### Архивы RAR

Измерено тестом `archive_timings` на настоящем комиксе (RAR 1.5-4 без сжатия, 68 страниц по ~0,7 МБ) и на 120 страницах по 2,9 МБ, упакованных WinRAR 7 в формат RAR 5, обычным и непрерывным архивом.

| Архив | Список | Страница 1 | Средняя | Последняя | Все по порядку | Все, 3 потока |
|---|---|---|---|---|---|---|
| Комикс, 68 страниц | 0,9 мс | 3,5 мс | 2,7 мс | 2,9 мс | 165 мс | 84 мс |
| RAR 5, 120 страниц | 0,5 мс | 10 мс | 8,4 мс | 8,1 мс | 1067 мс | 409 мс |
| RAR 5 непрерывный, 120 страниц, без курсора | 0,6 мс | 8,8 мс | 300 мс | 571 мс | ~35 с (оценка) | |
| RAR 5 непрерывный, 120 страниц | 0,5 мс | 9,2 мс | 311 мс | 303 мс (после средней) | 778 мс | 757 мс |

- Запись находится чтением заголовков перед ней; в обычном архиве их данные пропускаются, поэтому любая страница стоит примерно одинаково. Формат определяется по первым 6 байтам (~0,07 мс).
- В непрерывном архиве распаковываются все страницы перед нужной, поэтому без помощи последняя страница стоила ~570 мс, а миниатюры галереи — около полуминуты. Последний прочитанный архив хранит курсор UnRAR после последней прочитанной страницы и распакованные по пути страницы (до 256 МБ): чтение дальше стоит только страниц между ними, миниатюры всей книги — примерно одной распаковки, а потоки ждут распаковывающий поток, а не начинают каждый заново. Архив остаётся открытым, только пока показан именно он: UnRAR открывает файл без разрешения на удаление, поэтому чтение обложки для его ячейки в родительской папке оставляло его заблокированным, и переименование или удаление не удавалось. Показ другой папки отпускает его, не дожидаясь потока посреди прохода (он может длиться секунды и замораживал поток интерфейса); тот поток отпускает архив, закончив.
- UnRAR добавляет к exe ~290 КБ (со статической библиотекой времени выполнения C ему не нужна `MSVCP140.dll`), значок типа CBR — ещё ~50 КБ (306 КБ до того, как слои 256 пикселей значков стали храниться в PNG, см. [Запуск](#запуск)). Сначала была опробована обёртка `unrar-ng`: она зависит от `regex` с возможностями по умолчанию, из-за чего в exe попадали таблицы Юникода `regex` (~360 КБ), поэтому C API UnRAR вызывается напрямую через `unrar-ng-sys`.

### SVG

Измерено тестом `svg_file` на экране 2560x1440: классический тигр (513x525, 99 КБ) и значок 48x48 размером 40 КБ с градиентами.

| Рисунок | Разбор | Отрисовка в своём размере | Отрисовка для просмотра | Часть 3200x1800 при увеличении вчетверо |
|---|---|---|---|---|
| Тигр, 513x525 | 1,3 мс | 5,1 мс | 13,7 мс (1440x1474) | 26 мс |
| Значок, 48x48 | 0,5 мс | 0,3 мс | 25 мс (1440x1440) | 180 мс |

- Собственный размер рисунка (ширина и высота, иначе `viewBox`) считается размером изображения для масштаба, панелей, обрезки и сохранения, а текстура для просмотра рисуется крупнее, достаточно, чтобы заполнить экран при любой ориентации (`svg::view_scale`, не более 40 Мп), поэтому значок остаётся чётким в режиме «Заполнить окно». При увеличении сверх этой текстуры видимая часть с запасом в восьмую часть области с каждой стороны (последний столбец таблицы, для этого экрана) рисуется в отдельном потоке по пикселю на пиксель экрана (`detail`) и выводится поверх изображения, а когда она покрывает область при текущем масштабе — вместо него; до тех пор выводится, с масштабированием, часть предыдущего масштаба, и одновременно рисуется только одна часть, следующей — последняя запрошенная. Стоимость растёт с числом пикселей и с фильтрами размытия (как у значка), но не с масштабом. Альтернативой было считать размером изображения отрисованный размер: тогда значок 24 пикселя вписывался бы в окно в режиме «Вписать в окно» и имел бы 1440 пикселей при 100%, а его размеры указывались бы неверно.
- Системные шрифты (здесь 398) загружаются один раз, примерно за 19 мс, и только для рисунка с текстом; размер для галереи определяется без них.
- resvg (с текстом, SVGZ и встроенными растровыми изображениями) и значок типа файла SVG увеличили exe примерно на 1,5 МБ (с 13,39 до 14,93 МБ).

## Загрузка текстур

| Способ | Время потока интерфейса на фото 15 Мп |
|---|---|
| `load_texture` из egui (RGBA `glTexImage2D` + `glGenerateMipmap`) | 70–150 мс |
| Прямая загрузка через glow, BGRA `UNSIGNED_INT_8_8_8_8_REV`, уровни из рабочего потока | 3–10 мс (при прогретом пуле памяти драйвера) |

- Первый проход драйвера по новой памяти стоит около 25 мс плюс 1 мс на мегабайт, что бы ни делалось; прогрев лишь переносит эти затраты.
- Поэтому текстура начинается с mip-уровня, в котором показывается изображение (`GL_TEXTURE_BASE_LEVEL`), а уровни ниже загружаются позже, в свободном кадре, или сразу, когда они нужны виду: первое фото 14,7 Мп появляется примерно на 85 мс раньше.
- За кадр создаётся одна текстура (первой — текущего изображения), поскольку загрузка большой текстуры задерживает кадр.
- `glGetError` ждёт поток драйвера (20–60 мс), поэтому в сборках release он не вызывается.

## Кэш при листании

- Текстуры хранятся для текущего изображения, следующего по направлению движения, предыдущего и до трёх изображений дальше вперёд в пределах 100 миллионов пикселей (четыре фото по 24 Мп, около половины гигабайта видеопамяти).
- Каждое изображение считается таким же большим, как текущее, поэтому набор не меняется, пока декодируются соседние.
- Предыдущее изображение остаётся на экране, пока текущее не декодировано: пустых кадров не бывает.

## Миниатюры галереи

| Источник | JPEG 12 Мп |
|---|---|
| Кэш миниатюр Windows, миниатюра в кэше | ~3 мс |
| Кэш миниатюр Windows, миниатюры нет в кэше | ~30 мс |

- Миниатюры берутся из `IShellItemImageFactory` в размерах кэша Windows (96, 256, 768, 1280); сам qview декодирует их только для форматов, которые Windows не поддерживает (QOI, TGA, PNM).
- Миниатюра может быть увеличена до 1,5 раза, прежде чем запрашивается больший размер, поскольку размер 768 редко есть в кэше Windows и создаётся заново с девятикратным числом пикселей.
- Размеры изображений читаются из заголовков файлов; для JPEG qview сам разбирает сегменты до SOFn, поскольку декодер JPEG из библиотеки `image` читает весь файл даже ради размеров.
- Загрузка миниатюр ограничена по времени на кадр, а сверх бюджета пикселей вытесняются давно не показанные, но никогда не те, что нарисованы в последнем кадре.
- `cargo test --release thumbnail_timings -- --ignored --nocapture` с `QVIEW_THUMB_DIR` измеряет папку.

## Фильтрация

«Вид» → «Фильтрация» определяет, как фильтруется изображение, показанное не в масштабе 100%. Билинейная — собственная фильтрация текстуры, рисуется сеткой egui; бикубическая и пиксельная — собственные фрагментные шейдеры qview (`src/filter.rs`), рисуемые через обратные вызовы отрисовки egui_glow.

### Оценки, сделанные заранее

| Фильтр | Чтений текстуры на пиксель экрана | Видеокарта уровня RTX, область 2560×1440 | Встроенная Intel UHD 620, то же (оценка) |
|---|---|---|---|
| Билинейная | 1–2 (трилинейная) | ~0,02 мс | ~0,3 мс |
| Пиксельная | 1 | ~0,02 мс | ~0,3 мс |
| Бикубическая, увеличение | 16 | ~0,1–0,2 мс | ~2–3 мс |
| Бикубическая, уменьшение | 16–64 в зависимости от масштаба | ~0,1–0,5 мс | ~3–10 мс |

### Замеры

Тестовое изображение 6000×4000 в области изображения 2827×1652 (4,7 миллиона пикселей экрана), время работы видеокарты по запросам `GL_TIME_ELAPSED` в режиме `QVIEW_TRACE`:

| Фильтр | Уменьшение (41%) | 100% | Увеличение (125–1600%) | Сборка программы |
|---|---|---|---|---|
| Билинейная | ~0,05 мс | ~0,03 мс | 0,06–0,08 мс | — (не нужна) |
| Бикубическая | 1,0–1,4 мс | 0,8–1,7 мс (теперь рисуется сеткой) | 0,43–0,9 мс | 17,6 мс |
| Пиксельная | как билинейная | как билинейная | 0,13–0,48 мс | 8,1 мс |

- Первая программа за запуск собиралась 85 мс (запуск компилятора шейдеров драйвера), следующие — 8–18 мс.
- В первые секунды после открытия изображения билинейная показывала 1–8 мс, пока ещё загружались уровни полного разрешения; после их загрузки время стабильно составляло 0,03–0,05 мс.
- Отдельные кадры после простоя идут на пониженных частотах видеокарты, поэтому цифры скорее завышены.
- Бикубическая в 20–30 раз дороже билинейной, но 1–1,7 мс — это 6–10% кадра при 60 Гц и 25–40% кадра при 240 Гц. Худший случай, уменьшение чуть выше 50% (до 64 чтений на пиксель), ожидается на этой видеокарте около 3 мс, что всё ещё укладывается в кадр при 240 Гц.
- На слабой встроенной видеокарте бикубическая ожидается на уровне 20–40 мс на кадр в большом окне: прокрутка и анимация будут идти рывками.

### Решения

- **По умолчанию остаётся билинейная.** Она ничего не стоит на любой видеокарте и соответствует прежним версиям; бикубическая выбирается теми, кому нужна большая чёткость и чья видеокарта это позволяет.
- **Пиксельная фильтрация использует шейдер «sharp bilinear», а не `GL_NEAREST`.** При одном `GL_NEAREST` и нецелом масштабе пиксели получаются разной ширины (при 250% одни шириной 2 пикселя экрана, другие — 3) и дрожат при прокрутке; шейдер сохраняет каждый пиксель однородным и одинаковой ширины, сглаживая только границу шириной в один пиксель экрана, а при целом масштабе в точности совпадает с `GL_NEAREST`. `GL_NEAREST` остаётся запасным вариантом, если шейдер не собирается.
- **Бикубическое уменьшение берёт один mip-уровень, а не два.** Трилинейная фильтрация смешивает уровень с уровнем вдвое меньше, что смягчает изображения в масштабе от 50% до 100%. Бикубическая вместо этого берёт наибольший уровень, где на пиксель экрана приходится не более двух пикселей изображения, и растягивает ядро Catmull-Rom на область пикселя экрана (до 8×8 чтений).
- **При 100% бикубическая рисуется сеткой.** Её результат там совпадает с пикселями изображения, а сетка даёт его за шестнадцатую часть работы.
- **Программа собирается в кадре, следующем за первым, которому она нужна.** В первом кадре изображение рисуется сеткой, поэтому при запуске с выбранной бикубической изображение появляется так же быстро, как раньше; 8–85 мс сборки приходятся на время, когда оно уже на экране.
- **Mip-уровни усредняются в линейном свете.** Усреднение значений sRGB как они хранятся затемняет уменьшенное изображение всюду, где соседствуют светлые и тёмные пиксели: тонкие светлые линии, мелкая текстура и растр теряют вес при 25–70%, где показываются уровни 1 и 2. Теперь каждый уровень строится из предыдущего с переводом байтов в линейный свет по таблице, усреднением и обратным кодированием (непрозрачные пиксели идут коротким путём; полупрозрачный сначала делится на альфу, так что его цвет учитывается с весом альфы). Это стоит ~7 мс на фото 14,7 Мп в рабочем потоке и отключается в «Вид» → «Фильтрация» (декодированные изображения декодируются заново) для сравнения или ради прежнего вида.
- **Без причины ничего не перерисовывается.** egui рисует кадр только при вводе, анимации или загрузке, поэтому стоимость фильтра платится при прокрутке, масштабировании, листании и воспроизведении анимации, а не при простом показе изображения.

### Возможные улучшения

- Бикубическое увеличение девятью билинейными чтениями вместо шестнадцати точечных, а уменьшение — с частью чтений через аппаратную фильтрацию: примерно вдвое дешевле. Имеет смысл только для слабых видеокарт.
- Рассматривались масштабировщики пиксельной графики (xBR, ScaleFX, MMPX) и Lanczos: первые — длинные шейдеры для узкого применения, второй при увеличении почти не отличается от Catmull-Rom и даёт больше ореолов.
- Лучшее ядро для mip-уровней (Lanczos или Kaiser вместо усреднения 2×2) сделало бы чётче и билинейное уменьшение ценой примерно 15–30 мс дополнительного декодирования на фото 15 Мп в рабочем потоке (7 мс из них уже занимает усреднение в линейном свете).
- Отрицательный `GL_TEXTURE_LOD_BIAS` (около −0,3…−0,5) сдвинул бы трилинейную смесь билинейной фильтрации между 50% и 100% к большему уровню: резче без затрат на декодирование, с некоторым алиасингом на регулярных текстурах.
- Цифры для встроенной видеокарты выше — оценки, а не замеры: у тестовой машины встроенной видеокарты нет.

## Гистограмма

Раздел «Гистограмма» панели сведений подсчитывает уровни красного, зелёного, синего и яркости текущего изображения (`src/histogram.rs`). Свёрнутый, он ничего не стоит: пиксели не подсчитываются и ничего не хранится, лишь раз за кадр записывается флаг. Раскрытый, он поручает потокам декодирования подсчитывать каждое декодируемое изображение (`Meta::histogram`, 4 КБ на изображение), а изображение, декодированное до раскрытия, читается заново и подсчитывается в отдельном потоке.

### Замеры

Два изображения 5120×2880 (14,7 Мп), фотография (JPEG) и плавный градиент (PNG), подсчёт по премультиплицированному BGRA декодера:

| Подсчёт | Фотография | Градиент |
|---|---|---|
| Один набор счётчиков, пиксели с каналом в 0 или 255 подсчитываются попиксельно | 23–26 мс | — |
| Один набор счётчиков, обрезка берётся из крайних уровней | 15–23 мс | 65 мс |
| Четыре набора счётчиков для чередующихся пикселей, один поток | 18–20 мс | 19–20 мс |
| То же, до четырёх частей в потоках (используется) | 7–9,6 мс | 6–9,5 мс |

Что панель добавляет к открытию изображения:

| | Фотография | Градиент | JPEG 49,8 Мп (1520×32768, уменьшен до 12,5 Мп) |
|---|---|---|---|
| Декодирование, раздел свёрнут | 104–107 мс | 56–58 мс | 325–338 мс |
| Декодирование, раздел раскрыт (подсчёт параллельно с mip-уровнями) | 109–113 мс | 61–67 мс | 330–337 мс |
| Повторное чтение и подсчёт при раскрытии на уже декодированном изображении | 80 + 6 мс | 34–41 + 6–7 мс | 135 + 17–22 мс |
| Построение графика (три полупрозрачные области по 512 вершин и три линии) за отрисованный кадр | 6–9 мкс | | |

- При раскрытом разделе декодирование длится на 3–10 мс дольше, примерно на 5 %; для JPEG 49,8 Мп разница в пределах шума. Изображение появляется на столько же позже; соседние изображения декодируются заранее в любом случае.
- Результаты одного и того же теста различаются примерно на 20 %, так как ядра процессора различны (производительные и энергоэффективные) и работают на меняющихся частотах.
- Строки декодирования сняты декодером JPEG библиотеки `image`, до того как JPEG на диске пошёл через декодер Windows; важна разница между строками, которую декодер не меняет. Повторное чтение идёт через `loader::read`, по-прежнему библиотекой `image`.

### Решения

- **Подсчёт в потоке декодирования, а не в потоке интерфейса и не по текстуре.** Чтение пикселей обратно из GPU ждало бы драйвер; у декодера пиксели под рукой.
- **Подсчёт одновременно с построением mip-уровней.** Гистограмма подсчитывается в других потоках, пока поток декодирования строит уровни (~5 мс для 14,7 Мп), поэтому изображение задерживает лишь разница; подсчёт после уровней добавил бы все свои 7–10 мс.
- **Четыре набора счётчиков.** Соседние пиксели плавной области часто равны, и прибавление к только что записанному счётчику ждёт завершения записи: градиент подсчитывался 65 мс с одним набором и 20 мс с четырьмя.
- **Обрезка по каналам.** Подсчёт пикселей, у которых любой канал равен 0 или 255, занимал ещё половину времени четырёх гистограмм; вместо него доля каждого канала в 0 и 255 берётся из крайних уровней.
- **По полному изображению, а не по mip-уровню.** Уровень в 512 пикселей подсчитывался бы намного быстрее миллисекунды, но усреднение сглаживает пики, особенно в 0 и 255, ради которых гистограмму и смотрят.
- **Одно повторное чтение за раз.** Как и для остальных данных панели, при быстром листании с раскрытым разделом заново читается только изображение, на котором листание остановилось; изображения, декодированные при раскрытом разделе, повторного чтения не требуют.

## Цвет под указателем

Раздел «Цвет» панели сведений показывает пиксель под указателем. Свёрнутый, он ничего не стоит. Раскрытый, он поручает отдельному потоку заново прочитать текущее изображение из файла и хранит его декодированным в полном размере; пиксель затем находится при каждом движении указателя.

| | Фотография 14,7 Мп (JPEG) | Градиент 14,7 Мп (PNG) | JPEG 49,8 Мп |
|---|---|---|---|
| Повторное чтение в потоке при переходе к изображению | 81 мс | 38 мс | 134 мс |
| Хранится в памяти (RGB, 3 байта на пиксель) | ~44 МБ | ~44 МБ | ~149 МБ |
| Поиск пикселя под указателем | ~8 нс | ~8 нс | ~8 нс |

- **Файл читается заново, а не сохраняются пиксели декодера.** Соседние изображения декодируются заранее, поэтому к моменту, когда одно из них становится текущим, его пиксели уже загружены в видеокарту и освобождены; хранить их для каждого изображения в кэше стоило бы в несколько раз больше памяти. Кроме того, повторное чтение даёт полное изображение и тогда, когда видеокарта показывает его уменьшенным.
- **Одно чтение за раз.** При быстром листании с раскрытым разделом читается только изображение, на котором листание остановилось; прочитанное ранее освобождается, когда начинается следующее чтение.
- Повторное чтение идёт через `loader::read`, декодером библиотеки `image`, поэтому эти цифры верны и после того, как JPEG на диске пошёл через декодер Windows.

## Навигатор

Навигатор над увеличенным изображением — это та же текстура изображения, нарисованная второй раз шириной около 180 точек: видеокарта читает один из её мелких mip-уровней, которые есть у каждой текстуры, поэтому для него ничего не декодируется, не преобразуется и не загружается, и память не растёт. В кадре добавляются один текстурированный четырёхугольник и несколько прямоугольников, а кадры рисуются только тогда, когда рисуются и без него (масштабирование, сдвиг). Не измерялось: билинейная отрисовка всей области изображения занимает на тестовой машине ~0,05 мс видеокарты на кадр, а навигатор — малая доля её пикселей. Скрытие без действий требует перерисовки только на время угасания (0,3 с).

## Сохранение в PDF

Для «Файл» → «Сохранить в PDF» qview пишет PDF сам (`src/pdf.rs`, без крейта): страница на изображение, объекты каждой страницы пишутся по мере готовности, в памяти одно изображение за раз. JPEG (базовый или прогрессивный, 8 бит, серый или цветной, без поворота или повёрнутый по EXIF-ориентации) становится потоком `DCTDecode` байт в байт, PNG без прозрачности отдаёт свои данные `IDAT` как поток `FlateDecode` с PNG-предикторами; декодируются и кодируются только остальные изображения (сжатые с потерями — в JPEG с качеством 92, прочие — в быстрые данные PNG). Замерено `pdf_timings` на тестовой машине, файлы в кэше:

| Папка | Страниц | Файлы | PDF | Время |
|---|---|---|---|---|
| Скриншоты и фото, 31 PNG и 8 JPEG | 39 | 164 МБ | 164 МБ | 185–270 мс (5–7 мс на страницу) |
| Обои, 26 PNG, 8 JPEG, 1 WebP | 35 | 178 МБ | 175 МБ | 890–970 мс (25–28 мс на страницу) |
| Тестовый набор всех видов, 800x600, декодировано 12 из 18 | 18 | 3,1 МБ | 0,3 МБ | 294 мс (16 мс на страницу) |

- Страница, взятая как есть, стоит примерно столько же, сколько чтение и запись её файла; время уходит на декодируемые страницы (PNG с прозрачностью, GIF, BMP, TIFF, WebP, HEIC, SVG, отражённый или CMYK JPEG).
- PDF проверен `pypdf` в строгом режиме: таблица перекрёстных ссылок, декодирование каждого изображения, размеры и повороты страниц.
- Exe вырос на ~64 КБ (с 15 352 320 до 15 418 368 байт): кодеры, `flate2` и чтение JPEG и PNG в нём уже были.

## Пометки

Режим пометок (A, `src/annotate.rs`) ничего не стоит, пока не включён: шрифт не загружается, состояние не хранится. При включении изображение читается заново в отдельном потоке так же, как его читает сохранение (`edit::render`), и один раз считаются средние его блоков для каждой стороны блока, которую даёт размер блоков, — степеней двойки от 4 до 1024 (`annotate::mosaic`, `annotate::blocks`): область пикселизации на экране — это такая мозаика, пиксель на блок, увеличенная с фильтрацией по ближайшему соседу и обрезанная по области, поэтому перетаскивание ничего не стоит; при сохранении усредняются те же блоки тех же пикселей. Текст рисуется resvg в небольшое изображение — для экрана при каждом изменении и ещё раз при сохранении — любым из системных шрифтов: их база (та же, что у текста SVG) и список семейств загружаются в потоке, читающем мозаики, поэтому поток интерфейса их не ждёт. Рамки, овалы, линии, стрелки и линии от руки на экране — фигуры egui, в файле — контуры tiny-skia. Замерено `marks_sheet` на JPEG 3840x2160:

| Шаг | Время |
|---|---|
| Повторное чтение изображения (поток) | 65–67 мс |
| Его мозаики для блоков от 4 до 1024 (поток; 14 мс для трёх размеров, пока размер не стал плавным) | 43 мс |
| Загрузка системных шрифтов (поток; заголовки ~300 файлов) | 17 мс |
| Следующий текст (для экрана, при каждом изменении) | 2,4 мс |
| 17 пометок, нарисованных в изображении при сохранении (2 области пикселизации, 10 текстов четырьмя шрифтами, линия от руки из 200 точек) | 58 мс |

- Exe вырос на ~95 КБ (с 15 418 368 до 15 515 136 байт): resvg, usvg, tiny-skia и кодеры уже были в нём ради SVG и сохранения.

## Сохранение с уменьшением

«Сохранить с параметрами» уменьшает изображение в потоке сохранения после поворота, обрезки и пометок (`edit::resized`, Ланцош 3 из крейта `image`; изображение с альфой сначала премультиплицируется, чтобы цвет прозрачных пикселей не просачивался в соседние). Замерено `resize_timings` на RGB-изображении 6000x4000:

| До | Время |
|---|---|
| 75 % (4500x3000) | 505 мс |
| 50 % (3000x2000) | 381 мс |
| 1920x1280 | 285 мс |
| 10 % (600x400) | 194 мс |

- Достаточно быстро для одного изображения, сохраняемого в потоке: ни предварительного уменьшения блоками, ни другого крейта не нужно.
- Exe вырос на ~66 КБ (с 15 643 648 до 15 711 232 байт), в основном за счёт ресемплинга крейта `image`.
