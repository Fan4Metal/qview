# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

qview is a Windows-only image viewer, written in Rust with egui/eframe 0.36. Priorities: start-up speed, instant browsing, full keyboard control, no settings dialog. `README.md` / `README.ru.md` are the user-facing docs and must be kept in sync (both languages, cross-linked, formal tone). `doc/PERFORMANCE.md` / `doc/PERFORMANCE.ru.md` collect the measurements, estimates and decisions (test machine: i7-13700KF, RTX 4070 Ti SUPER, 3840x2160 at 240 Hz); add new measurements to both.

## Commands

```
uv run build.py                  # closes a qview.exe running from target\, then cargo build --release
cargo test                       # unit tests (view geometry, key map, folder order, decoder, mip levels, formats, thumbnails, folder tree, gallery grid, crop geometry, EXIF, saving)
cargo clippy --release --all-targets   # must stay warning-free
python tools/make_release.py     # tests, release build, dist\qview_<ver>_Setup.exe (Inno Setup 6, tools/setup.iss) and _portable.zip
python tools/make_release.py --no-tests --install   # the same, then installs it silently over the installed copy (closes it first; previous tasks reused)
$env:QVIEW_TRACE=1; .\target\release\qview.exe <file>   # start-up, decode and texture upload timings on stderr
$env:QVIEW_BENCH_FILE="<file>"; cargo test --release phase_timings -- --ignored --nocapture   # decode phases of one file
$env:QVIEW_ANIM_FILE="<gif or webp>"; cargo test --release file_frames -- --ignored --nocapture   # frames and delays of an animation
$env:QVIEW_THUMB_DIR="<folder>"; cargo test --release thumbnail_timings -- --ignored --nocapture   # gallery thumbnails of a folder
python tools/build_heif.py         # heif.dll + libde265.dll + licenses into target\heif\bin (build.py and make_release.py run it, then copy them next to the exe)
$env:QVIEW_HEIF_FILE="<heic>"; cargo test --release heif_file -- --ignored --nocapture   # libheif against WIC: header, decode times, pixel difference
```

Toolchain: stable MSVC Rust plus VS 2022 Build Tools. In the Bash tool, `cargo` is not on PATH; prefix commands with `export PATH="$HOME/.cargo/bin:$PATH"`. A running `qview.exe` locks the release binary; `build.py` closes it first (WM_CLOSE via `taskkill`, so settings are saved; killed after 3 s) and only touches copies under this project's `target`. The user often has qview open, so build with `uv run build.py`, not plain cargo. Heredocs containing Rust code break the Bash tool (lifetime apostrophes); write source files with the Write tool or a Python script.

## Architecture

- **`main.rs`** creates the `loader::Loader` and asks for the file from the command line *before* `eframe::run_native`, so decoding overlaps window creation (reference on an RTX 4070 Ti: main entered ~20 ms after process creation, window created ~145 ms, first frame ~160 ms; a 14.7 MP JPEG decodes in ~80 ms, so the window is the limit). The window icon is `embedded_icon(64)`, rasterised by `build.rs` (`icon::rgba(64)` at start-up took 6 ms). Renderer is **glow**, not the default wgpu, and image textures are uploaded directly (`texture.rs`). eframe default features are off (no accesskit, no wgpu). A window saved maximized is created normal (`MAXIMIZE_WHEN_SHOWN`; one saved in full screen is created maximized the same way), because winit shows a window created maximized before it is painted: a white flash. Maximizing it after eframe shows it appeared in two steps (normal size at (0,0), then maximized at (-11,-11)), so `App::new` cloaks it (`DWMWA_CLOAK`), maximizes it with `SetWindowPlacement` (`win::show_maximized`: the restore rectangle is the one saved as `window_normal` from `GetWindowPlacement`'s `rcNormalPosition`, not saved in full screen, or `DEFAULT_SIZE` centred; eframe saves a maximized window with its maximized size, and `ShowWindow(SW_MAXIMIZE)` left that as the size the window was restored to), and `App::uncloak` shows it once a maximized frame is presented (1 s timeout, so it can never stay invisible). Trace it by polling `IsWindowVisible`/`IsZoomed`/`GetWindowRect`/`DWMWA_CLOAKED` after launch. `normalize` repairs Explorer's `"C:\"` → `C:"` argument.
- **`instance.rs`**: one window per exe. `main` calls `instance::forward` before anything else is started: the first start owns the mutex `Local\qview.<hash of the exe path>`; a later one finds the message-only window of the class of the same name (made by `instance::listen` in `App::new`, on the UI thread, so winit's loop dispatches its messages), sends the normalized path in `WM_COPYDATA`, gets the main window back as the answer, calls `SetForegroundWindow` on it (the newly started process may) and exits. It waits up to 5 s for that window (the first start makes it ~150 ms in, or may be closing) and runs on its own if there is no answer. `App::ui` takes the last received path (`instance::take`) and opens it. A minimized window is restored by the message window; with a new path it is cloaked first (it would show the old image until the new one is decoded) and `App::uncloak` shows it once `current_on_screen` held at the start of a frame (`Cloak`, 1 s timeout), the same mechanism as the maximized start. Per exe path, so the installed copy and `target\release` do not take each other's files.
- **`loader.rs`**: N worker threads (2–3) take paths from a shared priority queue that the UI replaces wholesale (`Loader::want`), so files the user has skipped are never decoded; files being decoded finish anyway. A worker marks the file `done` before sending the result and `poll` clears that, so `want` never re-requests a file whose result is on its way; `Loader::forget` (called by `App::forget_files` after a save or undo) marks a busy or done file `stale`, and `poll` drops its result, decoded from the old contents, so it is asked for again. `decode` reads the whole file, guesses the format from content (extension as fallback), applies the EXIF orientation, shrinks to `max_side` (the GPU's `max_texture_side`, set on the first frame; 16384 before that) and converts to `Pixels`: premultiplied BGRA (the driver's native order) with every mip level, made by `half` (2x2 box, packed-byte averages) on the worker, so the UI thread converts nothing (14.7 MP JPEG: decode ~80 ms, BGRA ~14 ms, mips ~5 ms; `phase_timings` measures it). `Meta` keeps the file's real dimensions, so zoom percentages refer to the file even when the texture is shrunk.
- **`app.rs`**: `current` is the file the user is on, `shown` is what is on screen; `shown` stays the previous picture until the current one is decoded (no blank flashes), and `View::next_image` runs only when `shown` switches. `cache` holds textures of `wanted()` = current, the next in the direction of travel, the previous, and up to `AHEAD` more ahead within `CACHE_BUDGET` pixels (every image counted as large as the current one, so the set does not change while neighbours decode), and nothing else (`update_wanted`). Decoded results wait in `pending`: `poll_decoded` makes one texture per frame (the current image first), because a large upload stalls the frame. A texture starts at the mip level the image is shown at (`start_level`, `view::mip_level`); the levels below are uploaded from `partial` in a frame with nothing new to upload, or at once when the view needs them (`complete_current_if_needed`, before painting). Keyboard commands run before the panels are drawn; menu/toolbar/mouse commands are queued in `clicked` and run after, followed by a repaint. `run(Cmd)` is the single place where commands take effect. Deletion runs `win::recycle` on a thread (`poll_delete` then moves to the next image). Renaming (F2, `Cmd::Rename`, the File menu and both context menus) opens `App::rename`, a modal (`ui/dialogs.rs`, the name selected up to its extension as in Explorer, `folder::check_name` for what Explorer refuses, errors shown in it); `App::rename_to` renames with `std::fs::rename`, and `App::moved` moves the decoded texture, its pending levels, the gallery thumbnail, the selection and the favourite to the new path (nothing is decoded again), all pairs of a batch at once (every old name taken out before any new one goes in: `01→02, 02→03` would otherwise mix them up), then the folder is listed again for the new place in the order. Ctrl+Z (`Cmd::Undo`, File → Undo Rename/Save) undoes the last of `App::undo` (`Undo::Rename` and `Undo::Save`, each of one or several files, this session's, at most `UNDO_STEPS` and `UNDO_BYTES` of old contents): a rename back through the same `move_file`, a save by `edit::restore` (or deleting the file Save As made), with a notice; deletions cannot be undone (restoring from the Recycle Bin was judged not worth it). `App::modal_open` covers it with the other modals (keys and the wheel are theirs). When a listing does not contain `current` (deleted or renamed outside, or never there), `poll_scan` moves to the file that would follow it (`folder::insertion_point`) with a notice, so that browsing keeps working. Wheel browsing is accepted anywhere in the window (Windows routes the wheel to the window under the pointer) unless a popup or modal is open.
- **Rotating, flipping and cropping** (`crop.rs` state and geometry, `ui/crop.rs` the frame and the bar, `edit.rs` saving, `exif.rs`): `[`/`]` only turn the view (`View::turns`) and H/V mirror it (`View::mirror`: `View::flip` is a left-to-right mirror applied before the turns, so a mirror on screen also turns the other way; `view::paint` flips the UVs) until Ctrl+S (`Cmd::Save`, `App::save`) saves it; the status bar notes the angle. C (`Cmd::Crop`, `App::start_crop`) puts a `crop::Crop` over the image: the frame in pixels of the image as shown (turned), dragged by `crop::grip`/`crop::dragged` (edges, corners with or without `Aspect`, inside to move, outside for a new one), turned with the image (`Crop::turn`); the view switches to `Zoom::Fill` and gets its zoom back in `end_crop`. While cropping `input::Mode::Crop` maps Enter to Save and `App::run_in_crop` lets only zoom, panning, rotation and flips (`Crop::mirror`), full screen and the bars through; `check_crop` ends it when its image is no longer on screen. `App::save` sends an `edit::Job` (turns, flip, the crop in whole pixels unless it is the whole image, the upright size it was chosen on) to a thread; a format that cannot be saved over (`edit::can_overwrite`: not one of `edit::Format`, or a lossy WebP) goes through Save As (`pick_save_path`, rfd; the name from `edit::suggested_name`: `_crop`, `_rotate` or `_flip` added once, English in any language, numbered past existing files). `edit::save`: a JPEG only turned or mirrored gets its EXIF orientation composed with them (`turned_orientation`; `exif::with_orientation` adds a missing tag by copying the first IFD to the end, `exif::minimal` when there is no EXIF) and its XMP `tiff:Orientation` digit patched, the scan data untouched; anything else is decoded (`image`, or `loader::read_wic`), mirrored, turned, cropped and encoded (JPEG quality 92, PNG, lossless WebP, TIFF, BMP) with its ICC profile and EXIF (`exif::for_new_pixels`: orientation 1, Pixel X/Y Dimension, the IFD1 thumbnail unlinked). `edit::write_file` writes a temporary file beside it and `win::replace_file` (`ReplaceFileW`) puts it in place; a file saved over is not made anew if it was renamed or deleted meanwhile, and when `ReplaceFileW` fails with ERROR_UNABLE_TO_MOVE_REPLACEMENT (the original already gone) the temporary file is renamed into place or kept, never deleted. `App::still_saving` refuses another save or conversion while one runs or while `reloading` (the saved image not yet on screen again, the view still turned: a second Ctrl+S turned the file twice). File → Convert To (`Cmd::ConvertTo(edit::Format)`, `App::convert`; also the gallery's cell menu, `App::can_convert`: the current file need not be decoded, `Job::size` matters only with a crop, `edit` refuses animations) makes a copy beside the file without a dialog (`suggested_name` with no suffix, the view's turns applied, no crop), which `poll_save` only lists (`Saving::convert`), the original staying current. `poll_save` pushes `Undo::Save` with the old bytes and date, calls `changed` (decoded again, the gallery thumbnail forgotten, the folder listed again; `reloading` drops the view's turns once the new texture is on screen, so the old picture stays turned until then) and opens a file made by Save As. The encoders added about 230 KB to the exe.
- **`view.rs`**: scales are *physical* screen pixels per image pixel, the zoom shown (1.0 = 100% regardless of Windows scaling, 2.0 = 200%, above 1 enlarged; divide by `pixels_per_point` for points). `Zoom::Fit` never enlarges, `Zoom::Fill` fits with enlargement, `Zoom::Cover` fills the window and crops; the mode chosen with 1–4 (`View::mode`, `choose`, persisted as `zoom`) survives browsing, `Zoom::Scale` (from zoom steps) falls back to it on the next image, unless `View::keep` (L, not persisted) keeps the zoom and the pan offset for the next images (only the rotation resets). `place` clamps the pan offset and snaps the image corner to a physical pixel. Rotation is done by permuting UV coordinates in `paint`, not by rotating vertices. `mip_level(scale)` is the level a texture may start at: the nearest to the shown size, 0 from 71% up.
- **`wic.rs`**: Windows Imaging Component, for what the `image` crate cannot read (HEIC/HEIF and AVIF with the Store extensions, camera RAW, JPEG XR, DDS, any installed codec). The interfaces are declared by hand (`windows-sys` 0.61 has no Imaging module at all, so the GUIDs are written out too) and called by vtable index (`Com::method`, indices from `wincodec.h`); `wic::tests` checks them against Windows' own PNG and JPEG decoders. `decode` gives premultiplied BGRA (or straight RGBA for `loader::read`) and the EXIF orientation from the `System.Photo.Orientation` policy, not applied; `size` reads only the header (`header::read` uses it for these formats). `extensions()` (a `OnceLock`, warmed by a thread in `main`) is the installed decoders' extensions not in `folder::EXTENSIONS`, plus HEIC/HEIF/AVIF always (their error then names the Store extension, `wic::needs`); `folder::is_image` adds them to listings and the Open dialog, but not to the file associations. `wic::takes(path)` routes those extensions straight to WIC (RAW files are TIFF inside: `image` would show their small preview); other files try `image` first and fall back to WIC on failure (`loader::decode`/`read`). Callers keep COM initialised for the thread (the loader workers, the thumbnail workers, the Auto proportions thread), and each such thread keeps an uninitialised decoder of every container it has used (`wic::keep_codec`, released by the outermost `win::com_init` guard, which counts nesting): releasing the last HEIF decoder took ~260 ms (its HEVC pipeline shut down), so without it a 12 MP iPhone HEIC took ~280 ms for its header and ~500 ms to decode, with it ~5 ms and ~160 ms. The HEIF decoder applies the container's rotation itself and reports orientation 1 (a portrait iPhone photo decodes 3024x4032). `cargo test codec_list -- --ignored --nocapture` prints the installed decoders; `$env:QVIEW_WIC_FILE="<file>"; cargo test --release wic_file -- --ignored --nocapture` times one file.
- **`heif.rs`**: HEIC/HEIF through libheif 1.23 with libde265 built in (no plugins), loaded at run time (`LoadLibraryExW`, `LOAD_WITH_ALTERED_SEARCH_PATH` so `libde265.dll` is found beside it) from `heif.dll` next to the exe (tests also look in `target\heif\bin`); the C API is declared by hand (`Lib`, function pointers from `GetProcAddress`; `heif_error` is returned by value). Both are LGPL: separate DLLs, built with `/MT` by `tools/build_heif.py` (only `KERNEL32.dll` imported, no VC++ Redistributable), shipped with a `licenses` folder (texts, source URLs at the tags) by the installer and the zip; do not link them statically. `heif::takes` (extension heic/heif/hif and the DLL present) comes before WIC in `loader::read_wic` and `header::read`; a libheif error falls back to WIC, and its error is shown if WIC fails too (not the Store hint). libheif applies irot/imir, so orientation is 1 and `size` is upright. `size` reads through a `heif_reader` over a 64 KB `BufReader` (unbuffered it made ~30 000 small reads, 25 ms; now ~1 ms for a 12 MP iPhone HEIC). Decoding uses up to 8 threads (`heif_context_set_max_decoding_threads`; the default 4 took ~120 ms, 8 ~95 ms, WIC ~170 ms) and converts to premultiplied BGRA while copying out of libheif's plane. Issue #1 (wic_heic) led to it.
- **`anim.rs`**: animated GIF and WebP. `loader::read` sets `Meta::animated` (`anim::is_animated`: WebP's header flag; for GIF a second frame is looked for) and decodes the first frame as usual, so it is decoded ahead and shown like any image. `App::animate` runs a `Player` for the image on screen while it is current in the viewer (dropped in the gallery, on another image and in `on_exit`): a thread decodes the frames (`image`'s frame iterators, already composited on the full canvas) into a `sync_channel` two frames deep, so a long animation is never in memory whole, starting over for every loop until the file's loop count; `Player::poll` hands over a frame when the previous one's delay is over (kept to the schedule unless more than a frame late; delays under 20 ms count as 100 ms, as in browsers) and `Texture::replace` writes all its levels into the existing texture with `glTexSubImage2D`. The texture's `partial` levels are dropped when playing starts, since every frame fills every level. P (`Cmd::Pause`, `Player::toggle_pause`: the time the frame on screen had left is kept; an animation whose loops are over plays again) and `.`/`,` (`Cmd::NextFrame`/`PrevFrame`, `Player::step`, paused; View menu and the image's context menu, `ui::menu::animation_items`). Frames are not kept: a step back (or forward past the end) starts a new thread at the frame wanted (`play`'s `from`, frames before it composited but not converted; `anim::LAST` counts the frames first, for a step back from the first frame); `Frame::index` and `Player::index`/`count` (learnt when a loop wraps or ends) give the status bar's "paused on frame i of n".
- **`texture.rs`**: image textures are made with glow directly (`frame.gl()`, `register_native_glow_texture`), not with `ctx.load_texture`: egui_glow's RGBA `glTexImage2D` plus `glGenerateMipmap` took 70–150 ms of the UI thread per 15 MP photo on the RTX 4070 Ti (NVIDIA 610), BGRA with `UNSIGNED_INT_8_8_8_8_REV` and the levels from the worker take 3–10 ms once the driver's memory pool is warm. The driver's first pass over new memory costs ~25 ms plus ~1 ms per MB whatever is done (a warm-up only moves it), hence starting at the shown level (`GL_TEXTURE_BASE_LEVEL`) and completing later: the first 14.7 MP photo is on screen ~85 ms sooner. `glGetError` waits for the driver thread (20–60 ms), so release builds do not call it. View → Filtering (`view::Filter`, `App::filter`, persisted as `filter`): `filter.rs` paints the image through egui_glow paint callbacks with programs of its own (`filter::Program`, made in the frame after the first that wants it, `App::program_due`, so that a start-up with Bicubic chosen shows the image first: 8-18 ms, 85 ms for the first program of a run, on the RTX 4070 Ti; an empty VAO, corners from `gl_VertexID`, `App::paint_picture` chooses): Bilinear stays an egui mesh (the texture's trilinear filtering) and is drawn through a program only with `QVIEW_TRACE`, to be timed; Bicubic (Catmull-Rom with `texelFetch`: 4x4 enlarged, stretched over a screen pixel's footprint on the largest mip level with at most 2 texels per screen pixel reduced, up to 8x8; exact at 100%, where the mesh is drawn instead; premultiplied overshoot clamped; measured on the RTX 4070 Ti with a 4.7 MP image area: ~1-1.7 ms of GPU per frame against ~0.05 ms for bilinear); Pixelated above 100% ("sharp bilinear": LINEAR at coordinates moved so each pixel is flat and its edges blend over one screen pixel, equal widths at any zoom, unlike NEAREST). A program that cannot be made falls back to the mesh, `Texture::set_smooth` (`GL_TEXTURE_MAG_FILTER` NEAREST) for Pixelated. With `QVIEW_TRACE`, `filter` logs each program's build time and each new painting's GPU time (`GL_TIME_ELAPSED` queries read back in later frames, `Program::poll_timings`; a frame repainted to read them is not timed again). A dropped `Texture`'s GL texture is deleted by `texture::delete_dropped` at the start of the next frame (commands queued in `clicked` run after the image area is drawn, so a texture dropped then is still in that frame's shapes; deleted at once, the frame showed the driver's leftovers as white streaks), and by `App::on_exit` after it clears the caches while the context lives; `Picture` holds it in an `Rc`.
- **`input.rs`**: `command(key, modifiers, repeat)` is the key map (unit-tested), `gallery_command` its gallery variant; `1` is Actual, `2` Fit (shrink only), `3` Fill (fit with enlargement) and `4` Cover (fill and crop); numpad `/` and `*` remain as aliases. Numpad `*` has no `egui::Key` and arrives only as `Event::Text("*")`; `Ctrl+C` arrives as `Event::Copy` (Shift held: Copy Image); `Ctrl+V` arrives only through `win::watch_paste`. egui-winit falls back to the physical key when the logical one is not Latin, so letter keys work in the Russian layout. `ctx.options.zoom_with_keyboard` is turned off so Ctrl+Plus/Minus do not scale the UI. Only browsing, panning and zoom repeat when a key is held.
- **Gallery** (`gallery.rs` state and grid geometry, `ui/gallery.rs` drawing, `tree.rs`, `thumbs.rs`): `App::gallery_open` replaces the image area with a folder tree (left panel, width persisted as `tree_width`), a virtualized grid (only visible rows are laid out, `show_viewport`, positions from `gallery::Layout`) and a bar above the grid with the folder path, the cell proportions list (`thumb_aspect`, `gallery::ASPECTS`, the frame from `frame_size`: `thumb_size` is its long side; `None` is Auto: `Gallery::auto_aspect` reads the upright sizes of up to `AUTO_SAMPLE` images of the folder from their headers on a thread and takes the entry of `ASPECTS` most of them are nearest to (`common_aspect`), cached per folder, the previous proportions kept until then; when the proportions change, `Scroll::Keep` leaves the current image's row where it was on screen), the "Fill cells" check box (`thumb_fill`: `gallery::place_thumb` covers the frame and crops via UVs, and `side_needed` asks for thumbnails that cover the frame both ways) and the cell size slider (`thumb_size`). Entered with G/Enter/double click/toolbar (`Cmd::Gallery`) or Esc (outside full screen), left with the same except Esc, which closes the program there, or a double click on a cell (a click selects); a folder opened from the command line or dropped opens in it. It shares `files`/`dir`/`current` with the viewer: the selected cell *is* `current`, so Delete/Copy/Show in Explorer work unchanged; `App::run_in_gallery` overrides arrows (rows via `gallery::move_rows`), Page Up/Down (`Cmd::PageUp/PageDown`, only from `input::gallery_command`), +/- (cell size) and Esc. While it is open `wanted()` is only `current` plus the hovered cell after `HOVER_DELAY`, so a double click shows a decoded image. Double clicks use Windows' double click time (`win::double_click_time`, egui's default is 300 ms) and `input::double_clicked`, which also accepts egui's triple click (a selecting click followed by a double click counts as one, and was lost). A double click on the image counts only when the click before it was on the image too (`App::image_clicked`, cleared on leaving the gallery), so the tail of a triple click on a thumbnail does not go back, while a real double click right after opening does (a time guard made the first one fail). While the current image decodes, the viewer paints its gallery thumbnail at the image's size (`App::placeholder`) instead of the previous picture. Thumbnails: `thumbs::Thumbs` is a worker pool like `Loader` (wanted list replaced wholesale: visible cells first, then a screen ahead, half back); each worker is a COM STA thread (`win::com_init`) and calls `IShellItemImageFactory::GetImage` (`SIIGBF_THUMBNAILONLY`, vtable declared by hand since windows-sys has no COM interfaces) for Windows' thumbnail cache (~3 ms cached, ~30 ms uncached for a 12 MP JPEG), falling back to `loader::read` + `thumbnail` for formats Windows cannot (QOI, TGA, PNM). Sides are Windows' cache sizes (`SIDES`: 96/256/768/1280; cells 64-512 points), re-requested when cells grow; `side_needed` lets a thumbnail be enlarged up to `ENLARGE` (1.5x) before asking for the next size, because 768 is rarely in Windows' cache (made anew, nine times the pixels), and `place_thumb` enlarges a thumbnail only while it is smaller than its image. The cells requested ahead of and behind the visible ones are limited to `cells_in_budget`, and eviction (in `poll`, before drawing) keeps the thumbnails drawn in the last frame, so the grid never makes what it would evict. F5 raises `Thumbs`' generation: thumbnails started before it are dropped; it also reads the tree again (`Tree::refresh`: the top-level nodes, those still there kept, and every listed folder on one thread, the expanded first; `poll` merges a new listing by name, so expanded and listed sub-folders stay, and keeps `revealed` nodes, hidden folders the tree was taken down to). The image's real size is read from the header (`image_size`, swapped to match the upright thumbnail) by `header::read`: JPEG segment by segment up to SOFn with the EXIF orientation from APP1, because `image`'s JPEG decoder reads the whole file even for `into_dimensions`; other formats through `image`, whose decoders read only their headers (`header_timings`, ignored, compares the two). Textures go through `texture::Texture` (BGRA + mips from the worker), uploaded for at most `UPLOAD_TIME` per frame, LRU-evicted beyond `BUDGET` pixels. `tree.rs`: Pictures, Desktop (`win::known_folders`) and drives (`win::drives`, names from `SHGetFileInfoW` on a thread), each folder listed on a thread when first expanded (hidden ones skipped), then a second pass finds which sub-folders have sub-folders (arrows); `Tree::reveal` expands down to a folder as its parents get listed.
- **`editors.rs`**: File → Edit With (`ui::menu::editor_items`, also in both context menus) lists `App::editor_choices`: `editors::for_extension` (`SHAssocEnumHandlers` with `ASSOC_FILTER_RECOMMENDED`, "Open with"'s list, read on the UI thread when the submenu opens and cached per extension in `App::editors`; `IEnumAssocHandlers`/`IAssocHandler`/`IShellItemArray` declared by hand through `wic::Com`; qview left out), plus the kept editor if it is not among them; Other Program… picks an exe (`Editor::program`). An `Editor` is the handler's name (an exe's path, or a Store app's name such as "Photos") and its UI name; the one chosen becomes `App::editor` (persisted), which Ctrl+E (`Cmd::Edit`) opens; more than `EDIT_WITHOUT_ASKING` (5) files wait in `App::confirm_edit` for a yes (`dialogs.rs`), the editor chosen kept only then. `editors::open` runs on a thread: the handler of that name for the first file's extension is invoked with a data object of all the files (`SHCreateShellItemArrayFromIDLists` + `BHID_DataObject`), since Store apps start no other way, and with one file at a time if it refuses several (E_FAIL from Paint's); otherwise an existing exe is run with the files as arguments; with no editor kept, ShellExecute's "edit" verb. `cargo test print_editors -- --ignored --nocapture` (`QVIEW_EDITOR_EXT`) lists them, read only.
- **Choosing several images** (`selection.rs`; `App::selection`, a `Selection` of paths as listed, in the gallery only): Ctrl/Shift clicks (`App::click_cell`, the anchor is the last image clicked without Shift, else `current`), a right click keeps a chosen image's companions (`right_click_cell`), Shift with the moving keys (`input::gallery_command` gives `Cmd::SelectTo(Move)`, `App::grid_target`, `select_to`), Ctrl+A (`Cmd::SelectAll`), and a frame (`Selection::band`) dragged on `ui::gallery`'s background, which senses drags anywhere on the grid since the cells sense only clicks (the `ScrollArea`'s drag scrolling is off), its cells from `Layout::cells_in`, scrolling past the edges (`BAND_SCROLL`). Plain moves, a click on the empty space, Esc (before it closes the program), leaving the gallery and another listing clear it; a new listing keeps what is still listed (`retain_listed`); `moved` renames in it. With none chosen the current image counts as chosen; `App::targets` is what the file commands act on (the chosen ones in the grid's order, else `current`): Copy (`win::copy_files`), Delete (`confirm_delete` holds paths, `win::recycle` takes several, the shell's progress shown for more than one), Favorite (`toggle_favorites`, `Favorites::add_all`), Convert To (`convert_all`, `Saving` holds jobs done one after another, progress in the notice, one `Undo::Save` for all), Rename (`BatchRename`, `rename.rs`: `numbered` names in the grid's order, `check`, `rename_all` through temporary names with a rollback, one `Undo::Rename` for all). `Undo::Rename` and `Undo::Save` hold several files each.
- **`update.rs`** is the opt-in update check (`check_updates`, off by default; `last_update_check` limits the start-up check to one per `update::INTERVAL`, a day). `Updates::start` runs `latest_tag` on a thread: `win::https_get` (WinHTTP, `Win32_Networking_WinHttp`: the system's TLS and proxy, no HTTP crate) asks `api.github.com/repos/.../releases/latest`, which skips drafts and pre-releases, and `tag_name` picks the tag out of the JSON by hand. It compares with `CARGO_PKG_VERSION` (not `main::VERSION`, which carries the commit): `X.Y.Z-dev` comes before release `X.Y.Z`; release tags are never `-dev`. `App::ui` calls `Updates::poll`; a newer tag shows `toolbar::update_button` at the toolbar's right end, opening the release page (built from `CARGO_PKG_REPOSITORY`) with `win::shell_open`. About holds the checkbox, "Check now" and the outcome. `cargo test update -- --ignored` asks GitHub for real.
- **`folder.rs`**: lists a folder on a thread (`scan`), filters by `EXTENSIONS`, sorts in `App::sort` (`Order`: `SortKey` name/date modified/size and direction, View → Sort; the date and size come with the listing; name order is `win::logical_cmp`, `StrCmpLogicalW`, Explorer's order, also the tie-breaker), and always keeps the opened file in the list even with an unknown extension. Changing the order lists the folder again (`App::sort_by`) while the old listing stays on screen, then the gallery recentres on the current image. The "Sub-folders" check box above the grid (`App::deep`, not persisted; `App::set_deep` lists the folder again keeping the current image if it is still listed; folders chosen in the tree keep the mode, opening a file clears it) lists a folder with its sub-folders (`folder::list_deep`, visible sub-folders only, no symlinks or junctions): with "By folder" (`folder::Depth::ByFolder`) folder by folder in the tree's order (sub-folders in `logical_cmp` order, a folder's own images first), `Order` applying only within a folder; without it (`Depth::Flat`) all in `Order`; toggling it lists again (`App::relist`, as a new order does); `Scan` counts what it found (shown in the empty grid) and stops when dropped. `App::listing` (`dir`, or `dir\*` when deep) keys the gallery's per-folder state (scroll, Auto proportions); `App::display_name` is the path from `dir` when deep (status bar, cell tooltips). With "By folder" (`App::by_folder`, persisted; the check box is always shown, inactive without the sub-folders, so that the bar does not move) the grid is split into sections (`App::starts`, from `folder::starts`), each starting a row under a header (`gallery::HEADER`, `ui::gallery::folder_header`; a double click on a sub-folder's header opens it as the tree would, sub-folders still on, and reveals it in the tree); `gallery::Layout` is the grid's geometry either way (one section with no header otherwise): cell positions, the visible cells, `move_rows` across sections (headers are not rows); `Gallery::layout` keeps the last frame's for the keys. Opening a file always lists its folder alone. `history.rs`: every change of `dir` (the tree, a header, ↑, a file opened elsewhere; not the sub-folders check box or a new order) pushes the folder left as a `Place` (`App::here`: `dir`, `deep`, `current`, and in the gallery the current row's distance from the top, restored with `Scroll::Keep`) through `App::leave_for`; `Cmd::Back`/`Forward` (Alt+←/→, Backspace in the gallery as in Explorer, the mouse's side buttons `PointerButton::Extra1/2`, the toolbar) return to one (`App::return_to`), `Cmd::Up` (Alt+↑) lists `dir`'s parent, keeping `current` with the sub-folders. Gallery only; not persisted.
- **`clipboard.rs`**: Copy Image (Ctrl+Shift+C, `Cmd::CopyImage`: `Event::Copy` with Shift held; File menu and both context menus; allowed while cropping) renders the current image on a thread with `edit::render` (the decoding, mirroring, turning and cropping of `edit::save`, from the file at full size; the view's turns only when `editable`, the crop only while cropping) and puts it on the clipboard as `CF_DIBV5` (BITMAPV5HEADER, BGRA bottom-up with masks, sRGB; Windows makes CF_DIB/CF_BITMAP of it), plus registered "PNG" (fast compression) when it has transparent pixels. Paste (Ctrl+V/Shift+Insert, `Cmd::Paste`, File → Paste): egui-winit reads the clipboard's text for these keys and passes on nothing when there is none, so `win::watch_paste` installs a `WH_KEYBOARD` hook for the UI thread only (it only sets a flag, `win::take_paste`, read every frame and acted on when no modal or popup is open). `clipboard::paste` on a thread opens, in this order, the first existing file of CF_HDROP, a "PNG"/"image/png" (written as is), a CF_DIBV5/CF_DIB (`from_dib`: a BITMAPFILEHEADER put in front, decoded by `image`'s BMP decoder; masks after a 40-byte header for BI_BITFIELDS/ALPHABITFIELDS, palette), or an existing absolute path as text (quotes trimmed); images are saved as `Clipboard <local time>.png` (`win::local_stamp`, numbered by `edit::suggested_name`) in `clipboard::folder()`, `%TEMP%\qview`, and opened like any file. `App::clipboard` holds the thread's channel (`Clipped`), `poll_clipboard` takes it.
- **`print.rs` and `wallpaper.rs`**: File → Print… (Ctrl+P, `Cmd::Print`, `App::print`; also both context menus, for `App::targets`) and Set as Desktop Background (`Cmd::Wallpaper`, `App::set_wallpaper`, the current image only), both rendering through `App::as_shown` (the `edit::Job` Copy Image uses too: the view's turns and the crop only for the image on screen) and `edit::render_png` (fast PNG with the ICC profile) on a thread, `App::handing`/`poll_handed`. Print opens Windows' Print Pictures dialog, Explorer's Print for images: `CLSID_PrintPhotosDropTarget` (photowiz.dll) created and given `DragEnter`/`Drop` with a data object of the files (`editors::data_object`), on the UI thread (`print::show`, from `poll_handed`), since the dialog may call back into the data object. `print::prepare` passes a file as it is when `as_is` (JPEG/PNG/BMP/GIF/TIFF on disk, nothing turned or cropped, `header::orientation` none), otherwise renders it into `%TEMP%\qview\Print` (files older than an hour deleted first). `$env:QVIEW_PRINT_FILE="<file>"; cargo test print_dialog -- --ignored --nocapture` opens the dialog and times `Drop`. The wallpaper is written to `%LOCALAPPDATA%\qview\Wallpaper 1.png` or `2.png`, the one Windows does not show now (`SPI_GETDESKWALLPAPER`), and set with `SPI_SETDESKWALLPAPER` (`SPIF_SENDCHANGE` waits for every top-level window, hence the thread); the position stays the user's.
- **Filtering the gallery by name** (`App::name_filter`, the field in `ui::gallery::filter_field`, `FILTER_ID`: a magnifier button until wanted, `App::filter_open` for the frame it is asked for, then a field while it has the focus or text; `/` in the gallery (`input::gallery_command`; the `Event::Text("/")` of that frame is dropped, or the field focused in it would get it) and Ctrl+F (`Cmd::Find`, opening the gallery from the viewer) focus it): `App::listed` is the listing as it came, `files` what of it passes `folder::matches` (every word a substring of `App::display_name`, ignoring case; a word with `*`/`?` a mask for the file name, `folder::wildcard`). `filter_changed` filters anew without listing again (the current image stays if it passes, else the first that does; with none passing it stays current, index None); `poll_scan`, `moved` and `unlist` keep `listed` too, and a current image listed but filtered out goes to the first passing, not "File not found". `start_scan` clears the filter for another folder. While the field has the focus `App::ui` neither surrenders it nor runs key commands or Paste (Esc, which would close the program in the gallery, is the field's: it clears it). egui drops the focus on Esc in `Memory::begin_pass`, before `App::ui` runs, so the field keeps `App::filter_focused` from its last drawing (taken every frame) and that counts as having it. The status bar shows the filter with its count, the empty grid says nothing passes.
- **`archive.rs`** (ZIP and CBZ, crate `zip` with deflate only): an image in an archive has a virtual path, the archive's plus its name within it (`book.cbz\ch1\001.jpg`, `\` between folders: paths are compared as text); `archive::split` finds the archive among the path's ancestors (only names with an archive's extension are checked on disk), `read`/`metadata` read a file or an entry (the archive opened anew each time, entry names matched ignoring case and `\` vs `/`), and `loader::read_image`, `header::read`, `anim::play`, `edit::save`/`render` and the thumbnails (no shell thumbnail for them) read through them; only the `image` crate decodes them (`archive::list` lists only `folder::EXTENSIONS`, skipping `__MACOSX` and hidden names, `enclosed_name` against `..`). `App::open` of an archive file is `open_folder` on it (the first page, in the viewer); `start_scan` sets `App::archive` (never `deep`), `scan_dir` uses `folder::scan_archive` (`list_archive`: entries named by their path within the archive, so chapters stay apart; `by_folder` makes its folders sections), `mixed()` includes it, `display_name` is the path within it. Read-only: `changes_files` refuses Delete/Rename/Copy/ConvertTo/Edit/Favorite with a notice, the menu items are off, `can_overwrite` is false (Save goes to Save As, into `archive::folder_of`), Show in Explorer selects the archive, the tree reveals its folder (`archive::tree_folder`), headers and Go to Folder do not open its inner folders, the Sub-folders check box is off.
- **`favorites.rs`**: the favourites (S, `Cmd::Favorite`; the Favorites menu, the star button, both context menus), `favorites.txt` in eframe's storage dir: one path per line in the order marked, UTF-8, read once in `App::new`, rewritten through a `.tmp` + rename on every change; text after a tab is a later version's fields, kept as is; paths compared lowercase. The gallery lists them in place of a folder: `App::dir` is then `favorites::DIR` (`::favorites`, no folder can be called so), so history, the tree's selection (`tree::Kind::Favorites`, the first root, named when drawn) and the per-listing scroll work unchanged; `App::in_favorites`, `App::mixed` (sub-folders or favourites: sections with "By folder", no `insertion_point`), `App::scan_dir` (`folder::scan_files`/`list_files`: the paths that are files, grouped by folder in `logical_cmp` order of their paths or in one order). The favourites have their own order (`App::favorites_sort`, persisted as `favorites_sort`/`favorites_sort_descending`, `SortKey::Added` by default: the place in the file, offered in the Sort menu only there; `App::order` is the one in effect). Unmarking among the favourites takes the image out of `files` at once (`App::unlist`, shared with deletion). `renamed` and `poll_delete` update the list; a listing of the favourites drops those whose folder is there without them (`list_files`' `gone`, `Scan::take_gone`, read in `poll_scan`), keeping those of an unreachable folder (an unplugged drive); the same check (`folder::find_gone`, on a thread) runs at start-up, so that the count in the menu and the tree is right before they are listed (`App::poll_favorites_gone`, `forget_gone_favorites`). Go to Folder (`Cmd::GoToFolder`, `App::go_to_folder`, with the favourites or the sub-folders listed) lists the current image's folder alone, keeping it current, through the history. Copy All is `win::copy_files` (CF_HDROP), Copy All to Folder… `win::copy_to` (`SHFileOperationW` `FO_COPY` on a thread: the shell's progress and name conflicts).
- **Start screen and About**: `ui::app_icon` takes the smallest of the icons embedded at build time (`main::embedded_icon`, 64/128/256 px) not below the display size and minifies it with mipmaps (cached in `App::start_icon` / `App::about_icon`); `App::start_screen` shows icon, name, version and a hint when nothing is open; About (`dialogs.rs`) shows icon, name, version, description, author, and the homepage/license lines only when `repository`/`license` are set in Cargo.toml, plus where the settings live.
- **`ui/`**: `impl App` methods for the menu bar, the toolbar (icons are painted vector shapes, buttons use `Sense::CLICK` without `FOCUSABLE` so Space/Enter never activate them), the status bar and modals; in the gallery the toolbar has Back/Forward/Up instead of browsing, rotating and zooming, the gallery and delete buttons kept in place. `App::ui` also surrenders any widget focus before handling keys. A modal opened by a key ignores keys in that frame (`dialog_fresh`), otherwise F1 would close the Shortcuts window it just opened.
- **Window caption**: the window is created with the Windows theme and egui switches it to dark at the end of the first frame; Windows 10 repaints the caption with the new colours only on the next non-client repaint, so the caption was white until a focus change. qview is always dark, so `App::new` sets `DWMWA_USE_IMMERSIVE_DARK_MODE` (`win::dark_caption`: attribute 20, or 19 before Windows 10 20H1) while eframe still keeps the window hidden: the caption is dark from the first shown frame and nothing is repainted. Repainting the caption by sending `WM_NCACTIVATE` off and on visibly flickered it at start-up; do not bring it back. Check with a pixel probe of the caption in a `PrintWindow` capture.
- **`win.rs`**: Win32 helpers (`attach_parent_console` gives `--export-icon` the parent's console as stderr, since a GUI program started by Python's `subprocess` gets no handles; `com_init` returns a guard that uninitialises COM, Recycle Bin via `SHFileOperationW` with the main window as owner of the shell's questions, Show in Explorer via `SHOpenFolderAndSelectItems` on a thread (`explorer /select` hands the folder to the running Explorer, whose window Windows kept behind qview with a flashing taskbar button, even after `AllowSetForegroundWindow(ASFW_ANY)`), `explorer /select` as the fallback, `ShellExecuteW`, CF_HDROP via `clipboard-win`, local date via `SystemTimeToTzSpecificLocalTime` + `GetDateFormatEx`/`GetTimeFormatEx` in the user's locale, UI language, message box).
- **`icon.rs`** draws the app icon procedurally (two photo prints, the one behind tilted, the front one a sunset over mountains and a lake, `icon::photo`, which the file type icons reuse) and encodes `.ico` files (`encode_ico`); `cargo test icon::tests::preview_sheet -- --ignored` with `QVIEW_APP_ICON_SHEET=<png>` writes it at all sizes plus the small ones enlarged; `build.rs` includes it via `#[path]`, writes a multi-size `.ico` and embeds it with `winresource` as icon ID 1 (the lowest ID, which Explorer shows for the exe).
- **File associations**: `filetypes.rs` is the table of registered formats (ProgID `qview.<id>`, extensions, Type column names, icon band/letter colours from the classic 16-colour palette); each type has a `filetypes::Kind`: `folder::EXTENSIONS` must list the same extensions as the `Kind::Image` types (a test checks); `Kind::Archive` is CBZ (`archive`, opened as a folder, not listed in folders); the `Kind::Wic` types (HEIF, AVIF, RAW from `filetypes::RAW_EXTENSIONS`, JPEG XR) are decoded by `wic`, whose `extensions()` always includes them, so they are listed and routed to WIC even without their codec (the error then names the Store extension). `type_icon.rs` draws each type's icon at every size (page with a folded corner, the app icon's landscape from 32 px, a band with the extension in a 3x5 pixel font placed on whole pixels at a whole scale, so 16 px stays sharp); `build.rs` embeds them as icon IDs 101+ (`filetypes::icon_id`) and the registry refers to them as `"qview.exe",-<id>`. `cargo test preview_sheet -- --ignored` with `QVIEW_ICON_SHEET=<png>` writes a sheet of all icons at all sizes; `cargo test readme_image -- --ignored` with `QVIEW_TYPES_IMAGE=imagesile_types.png` remakes the README's picture of them (redo it when a type is added). `assoc.rs` registers per user under HKCU (ProgIDs with DefaultIcon and open command, `OpenWithProgids` of each extension, `Applications\qview.exe`, `Software\qview\Capabilities` listed in `RegisteredApplications`), then `SHChangeNotify(SHCNE_ASSOCCHANGED)`. It never writes `UserChoice` (protected by a hash; the default is the user's choice): "Choose as Default…" opens `ms-settings:defaultapps?registeredAppUser=qview`, and `assoc::defaults` reads `UserChoice` (else the extension's default ProgID) only to show the state: `Opener::QviewElsewhere` is a ProgID of another name whose command runs this exe (`HEIC_auto_file`, made by Explorer when qview was picked in "Open with" before it was registered for the type). An unclaimed extension (`assoc::unclaimed`: no default ProgID but qview's, no `UserChoice`, no other program in either `OpenWithProgids`) gets `HKCU\Software\Classes\.<ext>` default = qview's ProgID, removed again by unregistering. A ProgID Explorer made when qview was picked in "Open with" before it was registered for the type (`HEIC_auto_file`: only `shell\open\command`, kept as the user's choice even when qview is picked again, so the files showed the app icon and "HEIC File") gets the type's `DefaultIcon` and name when its command runs this exe (`assoc::other_prog_ids`), removed again by unregistering; `cargo test print_defaults -- --ignored --nocapture` (with `QVIEW_EXE`) shows both on this machine, read only. File → File Associations… (`dialogs.rs`) and `qview --register` / `--unregister` use it. Its test writes into a scratch key under `Software\qview_test_<pid>`, never the real associations; do not register the real build on the user's machine without asking.

## Conventions

- Every user-visible string goes through `tr!("English", "Русский")`; the language follows the Windows UI language (`i18n::system_lang`, set in `main`) unless chosen in About (`i18n::LangChoice`; applied in `App::new` from the settings and at once when changed). Strings are built every frame, so nothing caches translated text; the tree's top-level names come from Windows in its own language. Log messages and decoder errors stay English.
- Persisted state is only the window geometry (eframe `persist_window`), the toolbar/status bar flags, the image background, the zoom mode, the sort order and the gallery's cell size, fill choice and tree width (`save`, keys `toolbar`, `status_bar`, `background` as `#rrggbb`, `checker`, `filter` as `bilinear`/`bicubic`/`pixels`, `zoom` as `actual`/`fit`/`fill`/`cover`, `thumb_size`, `thumb_fill`, `thumb_aspect` as `16:9` etc. or `auto`, `tree_width` in points, `language` as `system`/`en`/`ru`, `sort` as `name`/`modified`/`size`, `sort_descending`, `favorites_sort` (also `added`), `favorites_sort_descending`, `check_updates`, `last_update_check` in Unix seconds, `by_folder`, `editor` and `editor_name` (see `editors`), `window_normal` as `left,top,right,bottom`); egui memory is not persisted. The favourites are user data, kept apart in `favorites.txt`. Do not add a settings dialog: the few choices live in the menus.
- The image area has no frame, so its background is `App::clear_color` (`App::background`, presets in `app::background_presets`, View → Background, whose colour picker is drawn inline in the submenu so the menu stays open). Text and the spinner drawn on it use `app::ink_on` to stay readable on light colours. Under the image (and the placeholder thumbnail) `App::paint_checker` draws a checkerboard (`App::checker`, persisted, on by default; `view::checker_texture`, 2x2 texels repeated with nearest filtering, squares a whole number of screen pixels from the image's pixel-snapped corner), seen only where the image is transparent.
- The release profile has `panic = "abort"`: any panic closes the program. `f32::clamp` panics when its bounds cross (a frame rounded a little past the image), so `crop.rs` uses its own `clamp`; sizes from files may be 0 (a GIF's screen), which `loader::read_image` refuses.
- The version comes from `Cargo.toml` (`main::VERSION`, shown in About and on the start screen). Between releases it is the next version with `-dev` (`0.2.0-dev`), and `build.rs` appends `git describe --tags --always` to it (`0.2.0-dev (v0.1.0-2-g4bd494d)`, rerun on commits, branch switches and new tags; no `--dirty`, which would go stale); a release version is shown as is. Release: drop `-dev`, commit, tag `vX.Y.Z` (release.yml checks the tag against `Cargo.toml`), then set the next `-dev` version.
- GUI checks: on this machine the OpenGL client area cannot be captured from outside: NVIDIA shows it through an overlay plane, so `PrintWindow` returns it white and `BitBlt`/`CopyFromScreen` shows the desktop behind the window, even for a normal-sized window; the rendering is checked by the user. The caption (non-client area) can still be probed with `PrintWindow` from a DPI-aware process (`SetProcessDPIAware`, otherwise the capture is cropped on a scaled display). Keys can be sent with `PostMessage(WM_KEYDOWN/WM_KEYUP)` to the window without touching the user's input; posted mouse moves are useless because Windows immediately reports the real pointer leaving. A launched qview window takes the focus, so whatever the user types at that moment goes into it (Backspace browses, Esc closes): warn the user before launching test windows. Before any simulated global mouse/keyboard input, warn the user too.
